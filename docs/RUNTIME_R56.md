# GhostC R2.36 — prevent stale diagnostics from being attributed to new acceptance sessions

## Verified gap

In R2.35, the acceptance report and `telemetry-latest.txt` carry the correct current session transaction ID and JAR SHA-256, but `Collect` blindly reads `config/ghostc/diagnostics-last.properties`. That file persists between runs and can contain numeric counters from a *previous install*. Therefore a new `Prepare` followed immediately by `Collect`, without ever launching Minecraft, could publish old FPS/ESP/snapshot counters beneath the new session's identity.

## Change

- `Prepare` records a metadata-only baseline before installation: `preparedUtcTicks` (UTC) and `diagnosticsBaselineModifiedUtcTicks` (0 if no earlier file). Both are stored in the guarded `install-state.json` **schema 2**. No original diagnostics file is copied, changed, or deleted.
- `Collect` admits numeric counters only if the file's last-write UTC ticks are **strictly later than both** the current Prepare timestamp and its pre-existing diagnostics baseline. An unchanged or backdated file results in an explicit `Withheld: diagnostics predates Prepare ...` status, *not* duplicated previous counters. Ordinary numeric-only privacy filtering remains intact.
- If a diagnostics file is genuinely updated after Prepare, `Collect` still appends its allowlisted numeric `count.*`, `perf.*`, and `snap.*` values to `telemetry-latest.txt`. It never replaces owner-written checkboxes or notes in the current acceptance report.
- Existing schema-1 install manifests continue to **Collect and Rollback** so a previous active installation remains recoverable. Because they lack timing provenance, their numeric diagnostics are withheld. A new `Prepare` always creates schema 2.
- Diagnostics freshness means **a local file changed after Prepare**, not that the genuine game ran. Filesystem metadata can be changed independently; the user must still inspect actual screenshots, build identity, GUI behavior and live tests.

## Windows CI acceptance fixture

The existing guarded Windows JDK8 Forge build/JAR/provenance plus two-session install/rollback suite now adds:

1. Before the first Prepare, seed `diagnostics-last.properties` with unmistakable stale counter `count.gui_open=99999`; keep its last-write timestamp older than Prepare. A first Collect (with no Minecraft launch) must **withhold** that counter.
2. After Prepare, rewrite the file with `count.gui_open=7`, `perf.p95_fps=144`, and a private-field fixture; set last-write strictly after Prepare. Repeated Collect must show the numeric fields, exclude the private value and preserve the owner's edited checklist byte-for-byte.
3. Complete guarded rollback, then a new Prepare of the **same JAR**. Its first Collect must **withhold** the last session's numeric `7` and keep a fresh unchecked report. The old report and sidecar must be archived byte-for-byte.
4. Update the file after the second Prepare with numeric `8` and `180`; Collect must refresh the sidecar without rewriting the checklist.
5. Convert the fake active installation manifest to schema 1 to model upgrade from an earlier release. It must still Collect (withholding numeric metrics) and Rollback correctly.
6. Exact PR-head and post-merge `main` Core Java 17/21 and Linux/Windows JDK8 Forge CI are separate required checks.

No Minecraft game, profile, network packet, UI module or combat source code is altered.

**Open boundary:** G1/G2/G4/G5 in-game acceptance, frame-rate measurements, visual correctness and real 60-minute stability remain unverified. An acceptance checklist is evidence collected by the owner, never a certificate generated by CI.
