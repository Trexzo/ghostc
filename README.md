# GhostC — modular Minecraft 1.8.9 client

**Milestone R2.69:** Java 8-compatible core, Forge adapter, original ClickGUI/HUD and shared gameplay service contracts. **Windows/in-game launch and visual fidelity are not yet verified.**

## What is implemented

- Host-independent registry, module lifecycle, typed settings, owner-thread policy, bounded event queue and profile persistence.
- `HostRuntime` receives client tick/render/input/world/disconnect transitions, isolates them from Minecraft objects, and persists toggles.
- Forge `@Mod` adapter under `forge189/`: world-only status/metrics HUD, F8 status toggle and F7 ClickGUI.
- New searchable ClickGUI: categories, settings, keybind capture, themed wide/compact layout; HUD editor with normalized positions and atomic preference persistence.
- R2.69 optional multiplayer ping metric: `hud.metrics.show_ping` (default false) shows already-received local tab-list latency as a distinct `PING 42 ms` row below FPS/XYZ. Invalid or absent entries are hidden, excessive values are bounded, and no extra packets are sent. The shared Status/Metrics layout and F7 HUD editor preview use identical measured fonts and footprints, preserving all existing pixel positions when disabled. Java8 tests cover 120,000 ping values, 85,000 HUD geometries and typed profile persistence. See [R2.69 ping HUD](docs/RUNTIME_R89.md).
- R2.68 crowded-team Target HUD completeness: when `hud.target.ignore_teammates` is enabled in **Nearest** mode, a snapshot packed with 256 closer teammates can otherwise evict every non-teammate from its visible partition before R2.67 filtering. The owner-tick snapshot now reserves its existing single optional pin for the closest range/visibility-eligible non-teammate, leaving the 256+256 shared budgets intact; the pin still has a strict 513-player overall cap. Crosshair's original single pin is unchanged because its mode is mutually exclusive; unfiltered HUD, Aim Assist and profile defaults are unaffected. Deterministic Java8 tests recreate 700 crowded teammates and 60,000 randomized nearest-candidate sweeps. See [R2.68 crowded team snapshot](docs/RUNTIME_R88.md).
- R2.67 opt-in Target HUD teammate exclusion: `hud.target.ignore_teammates` is disabled by default; when enabled, it hides teammates based on the local player's exact non-null scoreboard team object. Unlike a draw-only check, nearest selection skips a teammate and chooses the closest eligible **non-teammate**, preserving distance/ID tie-breaks; Crosshair mode suppresses an aimed-at teammate without changing the target. A second live team check protects against membership changes before drawing. Uses one reusable client-thread predicate, existing typed profile persistence and no additional LOS rays. Java8 tests cover 30,000 deterministic crowded target scenarios plus defaults/profile reload. See [R2.67 Target HUD team selection](docs/RUNTIME_R87.md).
- R2.66 opt-in Player ESP teammate exclusion: `render.esp.ignore_teammates` (default off) suppresses overlays for players with the same non-null live scoreboard team as the local player, regardless of team display prefixes, name colors or string labels. Filtering runs before nearest-budget admission and expensive LOS rays, then is repeated immediately before drawing to account for mid-frame team changes. Null/no-team players remain eligible and legacy profiles retain their original ESP output. Java8 tests cover 200,000 randomized team identities, team-change fencing, persistence and individual setting default reset. See [R2.66 teammate exclusion](docs/RUNTIME_R86.md).
- R2.65 focused-setting defaults: ClickGUI settings can now be restored individually with **R** when a setting row has keyboard focus (Tab to select). Unlike resetting the entire UI or profile, only that Bool, Choice or Number reverts to its original constructor default, through the validated owner-thread `UiActions.reset` gateway. Unchanged defaults do not trigger file rewrites, and key repeat is ignored. The existing R shortcut in the HUD editor and typing R in search retain priority. Seeded 40,000-case defaults tests include per-action persistence and restart/reload behavior. See [R2.65 setting defaults](docs/RUNTIME_R85.md).
- R2.64 keyboard-first module keybind capture: with module-list focus in the F7 ClickGUI, pressing **B** now arms the existing keybind editor without a mouse. Enter a subsequent key to assign it, Escape cancels and Backspace/Delete clears; reserved F7 and duplicate binds retain the existing validation and profile persistence. Search input, setting-row focus, HUD editor and modal capture take priority. Auto-repeated B/target keys never auto-assign while the capture prompt is active. Java8 regressions cover 140,000 randomized focus states, duplicate/reserved keys, clearing and owner-thread fencing. See [R2.64 keyboard bind capture](docs/RUNTIME_R84.md).
- R2.63 fault-recovery ClickGUI: modules in the registry's `FAULTED` state now visibly show a red `RESET` control instead of misleading `OFF`, and display a sanitized exception type when selected. Clicking, pressing Enter on the module, or using its assigned keybind clears the fault to Disabled without running the old crashing onEnable; a second deliberate toggle enables it. The same typed action and profile persistence path is retained. Core regressions cover faulting during enable/disable/events, mouse and keyboard recovery, owner-thread and recursion safeguards, and no private exception-text exposure. See [R2.63 safe fault reset](docs/RUNTIME_R83.md).
- R2.62 optional Target HUD distance readout: an opt-in `hud.target.show_distance` toggle (default off) adds a live player-to-target distance in blocks on a separate lower line. The formatter validates finite, in-range coordinates, uses Minecraft font measurements, and degrades to a compact abbreviation or hides text rather than clipping. The existing target card dimensions, name/health layout, skins, target selection and old saved profiles remain unchanged. Tests cover 100,000 randomized cases plus setting persistence. See [R2.62 Target HUD distance](docs/RUNTIME_R82.md).
- R2.61 ClickGUI search-focus ownership and Ctrl+F: while a search textbox is focused, typed characters, cursor navigation and shortcuts remain local to search instead of accidentally moving or toggling modules. Enter releases search focus without toggling a module; Tab transfers focus into settings; Ctrl+F focuses and selects the current query for immediate replacement. The existing explicit keybind-capture and HUD-editor semantics take priority. New Java8 focus-routing regressions include a 75,000-case seeded replay. See [R2.61 search focus](docs/RUNTIME_R81.md).
- R2.60 final ESP range/geometry fence: the Forge renderer admitted players to its nearest-80 set using positions and bounding boxes before painting, but a player or local camera could move or become geometrically invalid between admission and GL emission. Draw-time checks now re-read current positions, reject out-of-range or nonfinite geometry, and feed the same current squared distance to optional fade. The normal selection cap, visible-only setting, style palette, drawing order and combat paths are unchanged. Java8 tests replay 120,000 dynamic position cases. See [R2.60 live ESP paint gate](docs/RUNTIME_R80.md).
- R2.59 ClickGUI keyboard settings editing: after Up/Down module selection, Tab/Shift+Tab moves through that module's actual typed setting rows and scrolls to reveal them. Enter/Space toggles Boolean or cycles Choice options; Left/Right nudges Number settings by 5% through the existing validated/persisted UI actions. Search typing, keybind capture, HUD arrow nudges and mouse slider behavior retain priority. Java8 tests cover 45,000 seeded settings/viewport scenarios and typed-action persistence. See [R2.59 keyboard settings](docs/RUNTIME_R79.md).
- R2.58 crowded crosshair snapshot admission: the previous Crosshair Target HUD mode could miss an otherwise eligible aimed-at player when that player fell outside the existing nearest-256 visibility partition. An optional exact-live-world reticle player can now occupy one separate, current-tick pinned snapshot slot, without displacing the nearest buffers used by other features or changing ordinary Nearest HUD behavior. Pinned candidates still pass demand, live membership and health/range gates, are merged in stable distance/ID order, and are released on every tick/world reset. Java8 stress regressions cover crowding, duplicates, ordering and session cleanup. See [R2.58 pinned crosshair snapshot](docs/RUNTIME_R78.md).
- R2.57 Target HUD selection modes: original `nearest` remains the default; opt-in `crosshair` mode shows only the player directly under the current reticle, never an unrelated nearest player. The real Forge adapter validates the exact crosshair entity's current-world object identity before handing the ID to the pure snapshot/range/visibility gate; render-time live health/range checks remain in force. New typed choice persists through existing profiles. Java8 deterministic tests cover 30,000 snapshot scenarios. See [R2.57 Target HUD selection](docs/RUNTIME_R77.md).
- R2.56 Target HUD selectable skin: the Forge Target HUD now offers a persisted `hud.target.skin` choice (`classic` by default, opt-in `glass` with jade accent and thin outline). Existing classic pixel colors, HUD footprint, target admission and sanitized health labels remain unchanged; the immutable palette is reusable across frames without per-render allocation. Java8 tests verify original ARGB parity, choice persistence and 100,000 deterministic palette reads. See [R2.56 Target HUD skins](docs/RUNTIME_R76.md).
- R2.55 ClickGUI keyboard navigation: Up/Down now selects adjacent modules within the active category/search filter; Enter or Numpad Enter toggles that selected module. The selected row automatically scrolls into view without disrupting normal mouse wheel navigation. Module search, HUD arrow nudges and keybind capture keep priority over conflicting shortcuts, and empty filters cannot toggle a hidden module. Pure Java8 tests replay 40,000 filter/navigation transitions. See [R2.55 keyboard-first ClickGUI](docs/RUNTIME_R75.md).
- R2.54 module lifecycle re-entrancy: self-enabling/disable callbacks could re-enter a module before its state change committed; shutdown remained writable during arbitrary disable callbacks. ModuleRegistry now rejects recursive same-module transitions, seals shutdown before calling modules, and refuses shutdown inside uncommitted transitions. Failed disable callbacks run only once. Java8 tests cover self and cross-module cycles, shutdown mutation attempts, event-fault cleanup and 5,000 toggles. See [R2.54 lifecycle boundary](docs/RUNTIME_R74.md).
- R2.53 packet flush reentry boundary: the independent PacketCoordinator called untrusted transport and completion code during `flush` without preventing that code from recursively calling `flush` again. Nested calls could bypass the outer budget and recursively exhaust the stack. A scoped `flushing` guard now refuses nested flush calls and releases in `finally`, while normal callback submission, cancellation and session reset remain allowed. Java8 regressions verify budget, callback order, reset cancellation and 3,000 repeated nested attempts. No Minecraft networking/packet interception is added. See [R2.53 packet flush reentry](docs/RUNTIME_R73.md).
- R2.52 Aim Assist local-source freshness: R2.47 fenced target position immediately before a camera write, but absolute yaw/pitch were also computed using the snapshot's local position, yaw/pitch, and eye height. If the local player moves, rotates, or changes eye height after publication, the computed camera angles are no longer authoritative. A suggestion now retains the numeric source pose and refuses a stale source before applying camera rotation, including nonfinite values. Java8 tests replay 120,000 deterministic movements/turns/eye changes, and Forge wiring enforces pre-write ordering. There is no packet or target selection change. See [R2.52 Aim Assist source pose](docs/RUNTIME_R72.md).
- R2.51 action request phase identity: `ActionCoordinator` declared PRE_INPUT, SIMULATE and OUTPUT phases but keyed queued actions by owner plus type only, so two valid requests from the same module for one action type but different phases overwrote each other. Requests now use a stable owner/type/phase identity, and cancellation clears all phases, while existing one-consumption-per-action-type-per-tick, priority, generation and bounded 256-slot semantics remain intact. Java8 deterministic tests cover phase separation, replacements, capacity, cancellation and 4,000 tick cycles. No Minecraft-facing change, packet path or default settings are altered. See [R2.51 ActionCoordinator phase ownership](docs/RUNTIME_R71.md).
- R2.50 asynchronous ingress session fence: producer events previously remained in the bounded queue across world switches and disconnects, so an old-world event could be delivered to current-session modules on a later owner tick. HostRuntime now captures an atomic event-sequence boundary on every presence transition and disconnect, while BoundedIngress discards stamps at/before that boundary within the original strict 128-dequeue-per-tick budget. Even a producer that publishes an old-stamped event behind a new one cannot bypass the filter. Existing queue capacity and direct tick/world signals are unchanged; Java8 host tests cover join, switch, disconnect-after-leave, 256-event backlog and out-of-order publication. No game input/packet adapter behavior changes. See [R2.50 queue epoch fence](docs/RUNTIME_R70.md).
- R2.49 ESP exact-world player membership: unlike the snapshot and combat gates, ESP previously trusted playerEntities without verifying that the same player object still resolved in the live world's ID map. Replaced or despawned players could therefore produce a stale overlay. ESP now reuses the existing Java8 liveness/identity gate before LOS and again immediately before emitting GL geometry; the same visible-only, health, draw-budget, styling and opt-in settings remain unchanged. The regression adds 50,000 deterministic membership/lifecycle cases and source wiring guards. Real Minecraft runtime and visual acceptance remain outstanding. See [R2.49 ESP world identity](docs/RUNTIME_R69.md).
- R2.48 live Target HUD distance admission: the read-only target card selected from the owner-tick snapshot already refreshed health/death/invisibility before paint, but did not recheck distance after either player moved. The Forge redraw now suppresses a card when current target/local positions are non-finite or their live distance exceeds the saved target range, without altering selection policy, settings, combat, or gameplay writes. Java8 policy tests replay 120,000 bounded movement/distance cases and malformed coordinates; Forge wiring checks placement before label drawing. Actual on-screen behavior remains unverified. See [R2.48 live HUD distance guard](docs/RUNTIME_R68.md).
- R2.47 snapshot publication and camera-target freshness: the Forge tick snapshot previously revalidated an admitted player's health and coordinates, but did not ensure it still resolved to **the same entity object** in the active world before publication. A player could also become invisible or move outside an enabled target feature's range between admission and publication. The final visitor now checks world identity, updated distance and invisibility before including each entity. Aim Assist additionally validates the selected suggestion's live entity type, health, invisibility and **same-tick target coordinates** before applying any camera rotation; moving/despawning/replaced targets are suppressed without changing the vanilla input path. Reuses the existing `LiveCombatTargetGate` and adds 125,000 deterministic visibility/liveness combinations, target-position regressions and Forge integration ordering assertions. The final live check does not perform an extra raycast; LOS continues to come from the owner-tick snapshot. See [R2.47 snapshot and aim freshness](docs/RUNTIME_R67.md).
- R2.46 current-world crosshair admission: the Forge combat controller's renderer-cached `objectMouseOver.entityHit` previously counted as a valid target solely because it was a nondead `EntityLivingBase`. An entity might have despawned or been replaced in the live world under the same numeric ID, and NaN/depleted health could still pass. R2.46 requires the **same object reference** to resolve from the currently loaded world, with finite positive health and non-death, before allowing target-required Clicker/Hit Select/Block Hit policies to see it. Dead or nonfinite-health local players also suppress all synthetic combat writes. Vanilla physical clicks, opt-in defaults, and actual combat scheduling are otherwise unchanged. Java8 tests cover 160,000 randomized identity/liveness cases and 10,000 despawn/respawn identity swaps. See [R2.46 live crosshair combat admission](docs/RUNTIME_R66.md).
- R2.45 packet lifecycle callback isolation: the shared PacketCoordinator previously invoked stale/shutdown completion callbacks while still accepting submissions. A callback could enqueue a new request during `reset()` and carry it across the session boundary, or during `shutdown()` and leave it permanently pending without any completion. Reset now fences callback-driven mutations and detaches its old queue before notifications; shutdown marks the service stopped and detaches all queued work before any completion callback executes. Every previously accepted request still receives its proper STALE_SESSION or SHUTDOWN result exactly once, and a finished reset permits legitimate new-generation submissions. Deterministic Java8 regressions exercise reentrant callbacks, exception isolation, real SessionServices world transitions and 4,000 lifecycle loops; gameplay/network adapters remain untouched. See [R2.45 packet lifecycle completion safety](docs/RUNTIME_R65.md).
- R2.44 dual-scope rotation intent ownership: source audit of the Minecraft-independent G3 `RotationCoordinator` found that a module's `CAMERA` and `OUTBOUND` requests shared a map keyed only by owner ID, silently overwriting one another despite separate arbitration scopes. The coordinator now stores one request per (owner, scope) and cancels both scopes by owner; each scope's expiry, priority and tie order remain independent. Requests are also bounded at 256 total scoped entries, like the existing action coordinator, while replacing an existing owner/scope at capacity remains permitted. Deterministic tests cover double-scope admission, replacement, expiry, capacity, and 4,500 long-session ticks without target-world leakage. No Minecraft direct camera/packet hook or default module setting changed. See [R2.44 scoped rotation ownership](docs/RUNTIME_R64.md).
- R2.43 finite numeric slider correctness: the R2.41 click-and-drag slider interpolated as `min + (max-min)*fraction` and rendered its fill with `(value-min)/(max-min)`. While ordinary settings work, constant legal ranges `min=max` yield 0/0 and extreme finite endpoints such as `[-Double.MAX_VALUE,+Double.MAX_VALUE]` overflow to infinity and reject legitimate drags. The numeric setting constructor also unintentionally accepted a `NaN` initial value because neither range comparison caught it. New Java8 `NumericSliderScale` uses finite validated endpoints, constant-range handling, and overflow-resistant interpolation/normalized inverse mapping. Forge and UiActions use the same policy, while `Setting.Number` now rejects non-finite defaults. Deterministic tests cover 140,000 extreme-range cases, 100,000 ordered slider steps, exact endpoints, bounded profile writes and current ordinary-setting behavior. No gameplay, profiles or module defaults changed. See [R2.43 numeric slider range safety](docs/RUNTIME_R63.md).
- R2.42 live Target HUD validation: after selecting an entity from a tick snapshot, the overlay previously used the cached health for text/bar rendering even if the corresponding live player had since taken damage, died, or become invisible. The read-only Target HUD now checks the currently resolved player for valid finite positive health, non-death, local-player exclusion and the user's visible-only preference immediately before drawing; it reads live health for both the percentage and health bar. Snapshot selection and saved settings remain unchanged. Deterministic Java8 tests replay 120,000 state combinations and 18,000 stale-snapshot comparisons. This is a bounded on-screen correctness improvement, not a Minecraft runtime acceptance certificate. See [R2.42 live Target HUD](docs/RUNTIME_R62.md).
- R2.41 continuous numeric slider interaction: the ClickGUI previously treated number sliders as click-only controls—`mouseClickMove` handled HUD dragging but not numeric settings. ClickGUI now captures the stable module/setting ID and track geometry on left-button down, previews clamped 0–100% numeric values throughout the drag, and persists the profile **once** on mouse release (or cancellation due to resize, GUI navigation, scroll, or close) rather than writing a file for each movement. Pointer capture is revoked on cancellation, mouse button changes and viewport changes; no stale row can mutate another setting. Existing simple-click `UiActions.fraction` behavior and all default settings remain unchanged. Deterministic Java8 tests cover 16,000 seeded drags, extreme mouse coordinates, thread ownership, commit coalescing and cancellation. See [R2.41 continuous slider controls](docs/RUNTIME_R61.md).
- R2.40 ClickGUI Unicode label fitting: the GUI's legacy font-measurement loop truncated strings by `substring(...length()-1)`, which can split UTF-16 surrogate pairs (emoji/non-BMP characters) into invalid text, and rescanned successively shorter strings every frame. ClickGUI now reuses the Minecraft-font-aware Java8 `HudTextFit.fit` policy already used by Keystrokes/CPS, with one cached callback and bounded Unicode-scalar scanning. During the audit the shared formatter also proved capable of silently clipping input after its 64-codepoint safety limit without showing an ellipsis, even when the clipped prefix otherwise fit. This is now explicitly marked `...`, with long-form randomized Unicode tests and bounded font-call assertions. No GUI module defaults, keybinds, persisted positions or screenshot equivalence have been changed/claimed. See [R2.40 Unicode ClickGUI labels](docs/RUNTIME_R60.md).
- R2.39 visible-only ESP admission correctness: R2.38 ESP tested player line of sight but not Minecraft's invisibility flag. A truly invisible player with a clear ray could therefore still receive visible-only ESP overlays, while the shared Target HUD/Aim snapshot already rejected invisible entities. The renderer now excludes `EntityPlayer.isInvisible()` before LOS rays when `visible_only` is enabled, preserves unrestricted ESP behavior when disabled, and rejects NaN/infinite/depleted health prior to nearest-N admission. Host-independent randomized scene regression compares post-fix eligibility and LOS pruning with a straightforward reference selector, including invisible players, malformed health, stable ID ordering and geometry exclusions. Default visuals and other module settings remain untouched. Real in-game acceptance remains pending. See [R2.39 ESP visibility gates](docs/RUNTIME_R59.md).
- R2.38 rendered-work-aware hot paths: ESP previously selected and sorted the nearest **80** players every world render regardless of the configured `max_players` budget, then discarded entries above N. The reusable nearest buffer now applies a validated active N cap (1–80) *before* visibility rays/geometry; its default 80 remains unchanged, and the independent 256-player target snapshot remains untouched. Deterministic 420-frame/240-candidate replay compares all configurations and source order permutations against the legacy full-80 nearest top-N, including distance ties and rejected candidates. The optional diagnostics panel no longer formats all 14 rows when a small scaled viewport shows fewer; it evaluates just the layout-selected lines, and acquires FPS/snapshot statistics at most once each per visible panel. Full-size labels, line order and saved settings remain identical. No unmeasured FPS gain or in-game visual verification is asserted. See [R2.38 draw-budget efficiency](docs/RUNTIME_R58.md).
- R2.37 compensating Windows rollback: source audit confirmed the old rollback deleted the active JAR before moving backed-up originals into `mods/`; any mid-restore error left the profile only partly restored and the active transaction unretryable. Rollback now stages and hashes all original JAR copies *before* moving the installed client to a guarded temporary path; the state is removed only after every original is restored and verified. Handled restore failures remove the copied originals and move the exact active JAR back, retaining the transaction and backup originals so rollback can be retried. On incomplete compensation it fails closed and preserves recovery files rather than pretending success. A CI-only, temporary-profile-restricted deterministic fault hook tests failure after the first of two original JARs is restored, then validates exact two-JAR restoration on retry. This provides exception-safe recovery, not crash/power-loss atomicity or real Minecraft acceptance. See [R2.37 rollback recovery](docs/RUNTIME_R57.md).
- R2.36 stale-telemetry attribution hardening: R2.35 allowed a fresh acceptance transaction to re-label an old `config/ghostc/diagnostics-last.properties` report as current-session numeric evidence even if Minecraft never started. Prepare now records the old file's last-modified UTC ticks and the new transaction's UTC start in schema-2 `install-state.json`. Collect emits numeric counters only when diagnostics were modified strictly after **both** times, preserving the original file untouched. Pre-existing/unchanged files are explicitly **withheld**, even when a new report/checklist was generated, and new post-Prepare diagnostics continue to refresh the sidecar normally. Legacy schema-1 states can still Collect/Rollback, but without a trustworthy baseline their numeric exports are withheld. Windows CI seeds a stale 99999 counter before Prepare, verifies it cannot leak into either of two sessions, validates post-Prepare refresh, and confirms legacy state rollback. This is still metadata-only attribution, not proof of gameplay. See [R2.36 diagnostics freshness](docs/RUNTIME_R56.md).
- R2.35 backup-root junction hardening: the R2.34 Windows acceptance script checked the game, mods and acceptance directories for reparse points, and verified transaction backup children, but failed to reject a junction placed at the **parent** `ghostc-acceptance/backups`. That could redirect original JAR backup moves outside the intended profile and mislead rollback path verification. The acceptance utility now validates the existing backup root before Prepare/Collect/Rollback, checks the created root and transaction child again before moving any JAR, and rejects unexpected transaction directory reuse. Windows CI actively creates an external-target junction before Prepare and substitutes one after Prepare; it verifies that Prepare, Collect and Rollback reject the redirect, leave the current JAR and transaction intact, and do not alter an external sentinel. The existing successful two-session acceptance, evidence archiving and byte-for-byte rollback behavior remain tested. No real Minecraft launch is claimed. See [R2.35 filesystem safety](docs/RUNTIME_R55.md).
- R2.34 transaction-bound Windows acceptance evidence: audit found that R2.33 preserved checkboxes even after Rollback and a NEW Prepare, mistakenly reusing a previous gameplay test as evidence for another install. Repeated collection for the SAME session still preserves operator notes byte-for-byte; a NEW session automatically archives the previous human-edited checklist and numeric sidecar under a collision-safe `ghostc-acceptance/history/<unique-id>/`, then creates a fresh unchecked report—even when re-testing the identical JAR hash. Historical evidence is never silently deleted, installation and hash-validation behavior are unchanged. Windows CI runs a two-session same-JAR scenario, verifies archived bytes, new unchecked report, correct session identities and a second rollback. A 14,000-scene deterministic test suite checks both sides, exact original coordinates, malformed inputs, GUI settings and profile persistence. - R2.25 range-first ESP admission and optional player draw budget: The R2.24 Forge renderer performed an expensive canEntityBeSeen LOS ray before testing whether a loaded player was even within the configured ESP distance. Range/nonfinite rejection now occurs first, without changing the visible in-range player set. A new persistent `max_players` draw slider (1–80; default 80) reduces drawn overlays in crowds while preserving the independent nearest-80 candidate admission and choosing the closest N deterministically. For filled styles, that closest N subset is still painted far-to-near, maintaining R2.23 transparency ordering without drawing excluded farther candidates. Optional R2.24 fading now reuses the chosen entry's already-validated squared distance instead of recomputing it per drawn player; with fading off there is still no extra distance lookup. New Java8 `EspDrawLimit` policy and 9,000 reproducible crowd simulations test limits, ordering, and saved settings. These are source/CI optimizations, not claimed measured FPS improvements.
- R2.24 optional per-player ESP distance fading: adds `distance_fade` (default off), `fade_start` (0–90% of ESP range, default 50%), and `fade_min_opacity` (5–100% multiplier, default 25%) to the existing persisted Player ESP settings. When enabled, Box, Tracer, Skeleton, Corner and Filled wire alpha decreases linearly with player distance beyond fade start, reaching the configured floor at the range limit. Filled faces use the same per-player factor multiplied by the independent existing fill opacity; health bars retain their meaningful red/green coloring. The feature is completely bypassed when disabled, including its additional distance lookup, preserving legacy profile appearance and reducing crowd clutter only when requested. A pure Java8 `EspDistanceFade` policy and 18,000 seeded cases validate bounds, progression, malformed input, GUI/profile persistence and RGB independence. Actual Minecraft appearance remains unverified.
- R2.23 Filled Box transparency ordering: The R2.22 renderer submitted all six translucent faces in a fixed geometry order and drew nearby filled players before more distant ones, despite the renderer using alpha blending with depth writes disabled. For the two filled styles only, R2.23 submits the most distant players first and sorts each player's six existing faces by camera-to-face-center distance, farthest to nearest with stable original face-index ties. The pure Java8 `EspFilledBoxGeometry.emitBackToFront` validates every distance before emitting any vertices and reuses the exact original six quads without per-player allocations; the legacy `emit` API and all seven non-filled ESP styles remain unchanged. Wire outlines, skeletons, opacity settings, HP bars, GL state restoration and nearest-80 membership are preserved. 11,000 seeded camera/box scenes test exact face identity, ordering and malformed-camera isolation. The change improves source-level transparency ordering but real Minecraft visuals remain to be verified.
- R2.22 translucent Filled Box ESP: adds `filled_box` and `filled_skeleton` styles after the original seven ESP choices, with six transparent 3D bounding-box faces and a full RGB wire outline (optionally schematic skeleton). New `fill_opacity` slider 4–50% (default 18%) multiplies the existing RGBA opacity so fill and outline can have different transparency without changing the previous seven styles. The first-party Java8 `EspFilledBoxGeometry` checks finite and plausible-size bounds before nearest-80 admission, and emits exactly six quads / 24 vertices through a reusable sink with guarded `GL_QUADS`. Old style IDs/defaults, HP gauge, depth/through-wall controls, GL state guard, and profile schema remain intact. Tests cover 12,000 seeded boxes, all faces and slider/profile persistence; actual onscreen Forge render behavior remains unverified.
- R2.21 first-party 3D Corner Box ESP: adds optional `corner_box` and `corner_skeleton` styles to the existing Player ESP style cycle without reordering its previous five modes or changing the default. A new persistent `corner_length` slider (10–50% of the corresponding box dimension, default 26%) controls short inward-looking X/Y/Z arms at each of eight player bounding-box corners, rather than drawing the twelve complete Box edges. The new pure Java8 `EspCornerBoxGeometry` validates finite/nondegenerate player bounds before a candidate can enter the nearest-80 render selection, and emits exactly 24 GL line segments through one guarded batch without per-player arrays. Corner styles use R2.20 RGBA coloring, keep optional HP bars and existing depth/through-wall behavior, and share all original owner/fault safeguards. Regression covers 15,000 seeded geometries, seven mode decisions, slider settings and persisted style/length. Real Minecraft screen output remains unverified.
- R2.20 first-party customizable Player ESP appearance: the original Box, Tracer and schematic Skeleton line work previously used one hardcoded purple OpenGL tint. All five ESP modes now share persistent normalized `red`, `green`, `blue`, and `opacity` sliders inside the existing Player ESP settings. Defaults exactly preserve R2.19 purple and 82% opacity, with a valid alpha range 0.1–1.0 and channel range 0–1. The optional health gauge keeps its semantic red–green health fill rather than adopting the line tint. Color values are resolved once per render frame, with no per-player array allocations, and remain subject to existing owner-thread, profile validation and Forge GL restoration rules. Tests cover saved-profile round trips and 25,000 seeded RGBA combinations. This is source/CI-verified, not visually accepted in Minecraft yet.
- R2.19 bounded-rank profiler overhead reduction: Source audit found that `SnapshotTelemetry.snapshot()` recalculated p50/p95/p99 with three **4,097-bin linear scans** on every diagnostics HUD frame, once for aggregate timing and again for the last demand mode. Replaced with fixed-memory Fenwick order-statistic lookup (~13 steps per quantile and ~13 updates per sample), preserving the original exact nearest-rank percentages, 4096+ µs overflow bucket, uncapped elapsed maximum, four demand-mode partitions and strictly numeric opt-in export fields. Immutable per-bucket snapshot caching removes repeated recalculation and allocation when no new data arrived. The 72,000-sample independent regression oracle exercises all modes, extreme duration values, owner-thread isolation and report compatibility. This is bounded complexity validated offline, not a measured game FPS improvement.
- R2.18 classified snapshot profiling and focus isolation: R2.17's one aggregated p95/p99 distribution mixed off/visible-only/unfiltered/mixed target modes and included samples while Minecraft menus/chat/alt-tab had blocked input. The profiler now preserves the original numeric aggregate report and adds four separately bounded demand-class histograms and exported `snap.mode_*_` numeric fields; the diagnostics HUD identifies the last sampled mode and that mode's own p95/sample count. The Forge profiler starts only with Runtime Diagnostics enabled and the game in focus; no focus-blocked work is sampled. New tests verify 16,000 classified samples, privacy, ownership and mode counts, preservation of the old report keys and omission of menu samples. These are preparation for a comparable in-game benchmark, not measured FPS improvements.
- R2.17 opt-in snapshot work profiler: actual Forge client END-tick snapshot construction now produces a bounded 4,097-bin microsecond distribution (p50/p95/p99, uncapped max), as well as scanned-player, in-range, line-of-sight-query and published-target totals. Collection is strictly gated by the existing Runtime Diagnostics module, occurs only after a successful immutable snapshot publish, and exports numeric-only `snap.*` aggregates in the standard optional local acceptance report. The diagnostics HUD displays snapshot timing and workload next to the existing FPS/JVM-heap and ESP counters. Deterministic tests cover 16,000 replayed samples, privacy, opt-in behavior and quantile consistency. This is measurement instrumentation, NOT a claim of improved FPS or real gameplay testing.
- R2.16 independent target radii and allocation-free selectors: split snapshot LOS-gating by each active visibility preference's actual maximum radius. In mixed modes with a 24-block unfiltered HUD and six-block visible-only Aim Assist, only the inner six-block players now require LOS rays; distant HUD candidates still enter the unfiltered partition without extra rays. In the opposite configuration, the 24-block visible-only HUD still receives its full set, while hidden targets past unfiltered aim radius are excluded. Target HUD now scans for its nearest target without a sorted list, and Aim Assist scans eligible snapshot entries directly without materializing/sorting up to 512 candidate records each tick. Deterministic tests compare the new selectors against the original sorted path across 1,800 seeded worlds and 18,000 demand cases. No live FPS or gameplay parity is claimed.
- R2.15 demand-aware snapshot cost containment: the R2.14 Forge END-tick publisher performed LOS rays on every eligible loaded player regardless of whether Target HUD or Aim Assist was enabled, and regardless of the configured target range. The new first-party `SnapshotDemand` policy computes the active 24-block-maximum HUD and 6-block-maximum Aim Assist radius once per tick and rejects out-of-range candidates before LOS queries. If neither target consumer is enabled, it skips enumeration and still publishes an **empty valid** tick snapshot for unrelated combat safety gates. An unfiltered-only consumer performs **zero LOS rays** and uses just one capped nearest-256 group; visible-only and mixed modes preserve accurate visibility and original nearest-target semantics with up to 512 combined candidates. Deterministic tests cover 18k demand combinations and 1,350-player scenes; real FPS remains unmeasured.
- R2.14 visibility-aware target snapshot admission: fixes another crowded-world starvation case: an otherwise nearer 256-person group hidden by walls could exclude every visible Target HUD or Aim Assist candidate from the shared snapshot, despite their `visible_only` setting. Forge now retains the nearest 256 visible **and** nearest 256 nonvisible candidates in a reusable owner-thread partition, merging by distance/ID before constructing the immutable snapshot (512 max). Explicit duplicate-ID handling favors admitted visible records and nearer duplicates; raw player references are released after each publication. Target selectors and existing GUI/settings keep their semantics, and ESP still independently renders only its nearest 80. Tests cover 800 crowded players, target visibility, shuffled input, 190-tick churn and privacy boundaries; no in-game behavior is claimed.
- R2.13 nearest-256 shared world snapshots: Target HUD and Aim Assist previously used only the first 256 valid players encountered in Minecraft's arbitrary loaded-player list. The Forge snapshot publisher now uses the existing nearest-first bounded owner-thread buffer at capacity 256, validating finite pose, positive health and distance before admission. Its output is a newly built immutable snapshot, and raw player references are always cleared in a finally block. ESP retains its independent 80-player render cap. New deterministic regression covers 700 loaded players with near targets at the end, 128 shuffled lists and 250 simulated crowded-world ticks; real Minecraft gameplay acceptance is still outstanding.
- R2.12 nearest-player ESP priority: the 80-player per-frame cap now uses a deterministic nearest-first selection instead of trusting the arbitrary order of Minecraft's loaded player list. A reusable, owner-thread-only bounded buffer orders candidates by squared distance and entity ID (stable ties), rejects duplicates/invalid distances, and clears entity references after each render. All pre-existing filters and full finite geometry/skeleton validation run before admission, so an invalid or distant candidate cannot consume the available 80 slots. All five ESP styles and the optional health bars share the same closest-player selection. Core tests verify order invariance with 280 shuffled populations and a 1,000-frame replay; in-game visibility remains unverified.
- R2.11 optional ESP health bars: adds a GUI-toggleable, persisted `render.esp.show_health` option (disabled by default for legacy profile compatibility) alongside all five pre-existing ESP styles. First-party, allocation-free camera-facing vertical health geometry (background plus green-to-red fill) works beside boxes, tracers and skeletons, honors existing depth/through-walls, and skips malformed health/width/view data without disabling valid ESP primitives. Includes seeded 14,000-pose geometry and cross-style wiring tests; actual Minecraft visual fidelity remains unverified.
- R2.10 focus and warning visibility hardening: END-tick focus admission now suspends FPS timing even when Forge stops issuing 2D overlay callbacks in a GUI. The owner runtime rejects performance samples while its input focus is blocked, and unadmitted world/player overlay events clear timing references. Reversed/overflowed monotonic timestamps are counted separately rather than corrupting FPS bins. Fault/profile/UI/diagnostics warnings appear even when both Status and Metrics modules are disabled, using bounded fallback positioning. Offline tests model no-overlay GUI gaps and 13,000 seeded viewport sizes; live Minecraft startup/visual acceptance still needs real evidence.
- R2.9 active gameplay performance telemetry: optional diagnostics now samples actual Forge overlay callback intervals into a fixed 1001-bin FPS histogram (min/p50/p95/p99/max, rounded FPS), and tracks sampled JVM heap/peak MiB. GUI/chat/focus/world changes or turning diagnostics off suspend the interval timer. Counts and heap aggregates export as safe numeric fields in the existing Windows acceptance report; no process, player, server or chat data is retained. These measure callback cadence rather than confirmed displayed pixels, GPU timings or a completed gameplay soak.
- R2.8 in-game ESP diagnostics bridge: counts actual client-thread ESP renderer frames, submitted player draws, submitted skeleton draws, and rejected invalid geometry without retaining player names, locations or server details. The in-game opt-in diagnostics HUD and local counter-only export surface those counts. Validates both current and previous skeleton body yaw, render interpolation fraction and height on **all** ESP modes before GL vertices are issued. Adds a versioned acceptance checklist to cross-check visible results, but no automated test claims a successful Minecraft GUI launch.
- R2.7 original skeleton ESP: adds selectable `skeleton` and `box_skeleton` modes alongside the existing `box`, `tracer`, `both`. A first-party Java-8-compatible body-oriented schematic 15-bone player overlay supports interpolation, movement swing and crouch. Rendering retains the existing visibility, depth, range, style and OpenGL guards. Only fully validated players count against the per-frame 80-player cap. Deterministic 14,000-pose regression replays and JAR class-inventory checks are included; visual results remain unverified in game.
- R2.6 recovery transaction and bounded read: the actual input stream is capped at 1 MiB (including concurrent growth); legacy schema-1 files are also limited to 4096 parsed fields. Failed typed validation of a backup can no longer modify live module or UI settings before file recovery succeeds. Restoration promotes the **same exact staged and validated backup bytes** rather than applying one revision and restoring another.
- R2.5 typed backup validation: profiles and UI backups are checked against the **same complete typed settings parser used at load time**, in addition to the canonical SHA-256 digest. Correctly sealed but unloadable keybinds, enums or HUD positions can no longer replace a known-good .bak. Both success and negative paths are regression-tested.
- R2.4 backup rotation hardening: module-profile and UI saves now verify the exact staged source bytes, canonical digest and schema before replacing the prior .bak. A damaged or legacy unsealed primary can be overwritten with a new healthy save **without poisoning the last verified backup**; atomic promotion and temporary-file cleanup protect existing backups. Seeded corruption-and-save regression tests and Forge source contracts prevent reintroduction.
- R2.3 config resilience: modern module profiles and UI preferences include a canonical SHA-256 corruption check while legacy schema-1 files remain readable. Startup can restore validated .bak copies without overwriting the only good backup, preserving damaged originals as .corrupt. Oversized config files and malformed digests are rejected before any state mutation.
- R2.2 bounded Status/Metrics renderer: measure the combined Status/FPS/XYZ footprint so metrics-only HUDs and long coordinates remain screen-anchored. Status and Metrics now render through separate fault guards, and the F7 editor uses their measured footprint. Includes seeded geometry and independent fault-isolation regression coverage.
- R2.1 accessible HUD controls: dedicated Status/Keys/CPS/Target selector tabs, one-pixel arrow nudges (Shift+Arrow 10 pixels), and a reset action. Live editor previews and the actual Forge renderers now share settings-dependent Keystrokes/Target HUD heights, preserving normalized anchors and UI schema-1 persistence.
- R2.0 viewport-accurate HUD editor: a letterboxed representation of the actual Minecraft scaled screen replaces the stretched editor canvas; preview widget footprints, normalized drag coordinates and rendered anchors now share a pure geometry model, with automatic status size/scale parity. This corrects visual misplacement on widescreen aspect ratios while retaining all R1.9 widget preferences.
- R1.9 multi-widget HUD editor: Keystrokes, CPS and Target HUD now have separate draggable normalized anchors alongside the original Status HUD. The existing UI profile schema and status position remain backward-compatible; new coordinates are validated and persisted atomically. Forge renderers consume these anchors instead of hardcoded screen offsets.

The capture dialog now lets F7 close the GUI. A deterministic 10k-key replay and negative profile tests verify rejection without partial changes.
- R1.7 Compact GUI recovery: replaced the impossible 445px minimum (Compact maxes at 390px) with geometry-derived safe boundaries so Compact and Wide both work; reconciles selected module with current search/category results, preventing hidden settings/keybinding edits and handling zero results safely. Automated tests validate resize/toggle behavior and 25k seeded selection transitions.
- R1.6 ClickGUI chrome safety: header tabs/layout/theme controls and sidebar category clicks share exact visible geometry, while undersized scaled viewports display a resize notice and disable ambiguous controls. The module registry now retains exception types without private exception messages; both behaviors are protected by new Java and Forge-wiring tests.
- R1.5 immediate render/input admission: reject mouse and both 2D/3D render callbacks that arrive after an unadmitted world/player swap but before the next END tick; visible-row-only ClickGUI module and setting hitboxes, bounded wheel regions and reliable small viewport click handling. New seeded `ViewportHitTests` and Forge wiring gates guard against regressions.
- R1.4 session correctness: detect world/dimension/local-player object identity replacements without an empty-world tick, invalidate both old session generations and stale snapshots, skip malformed player poses, and reject nonfinite ESP geometry before calling OpenGL. All backed by direct Forge wiring and seeded lifecycle regression tests.
- R1.3 combat reliability: independent Java exception quarantine for Aim Assist, AutoClicker, Hit Select and Block Hit with fail-closed action/camera intent cancellation. Enhanced pure-Java session/fault replays and real Forge combat wiring checks, plus one shared mod version constant for both in-game HUD labels.

- New Java/Python regression gates verify both the pure feature fault behavior and its actual Forge source wiring so later refactors cannot silently bypass the guard. **In-game rendering, input and stability remain unverified.**
- R1.1 ClickGUI viewport fixes: search hitboxes and focus rebind on scaled-screen changes; HUD editor preview and list geometry cannot exceed the window, and F7 can also close the GUI.
